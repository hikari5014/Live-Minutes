01 · 問題定義

純中文模式已經可用，但沒有為中文最佳化

現況：設定「中文 → 不翻譯（純逐字稿）」即進入純中文模式，翻譯不呼叫、DeepL 歸零， 只花 Deepgram（辨識）＋一次 Gemini（紀錄）。房間端也已有同語言防呆。 問題不在功能缺失，而在中文特有的品質陷阱沒有被處理。

✅ 現在就能用的既有槓桿

設定中的「翻譯分段」不只作用在翻譯——它是把連續句子合併後才成段，純逐字稿模式下同樣生效。 中文 ASR 常吐很短的片段，把它調成「中／長」，逐字稿會從碎句變成通順段落。 代價：此設定目前的命名與說明（強調省 DeepL 額度）對純中文情境是誤導的，應更名為「逐字稿分段」並改寫說明。

中文特有的五個痛點

1引擎選擇（最重要，且反直覺）

目前邏輯是「只要開語者分離就走 Deepgram」，而語者分離預設開啟。 但 Deepgram 的中文表現一般弱於其英文，而瀏覽器 Web Speech（Chrome／Android）背後是 Google 引擎， 台灣國語表現通常很好而且免費。等於純中文會議可能正在用較差的中文引擎，去換發言者標記。

⚠️ 例外：iPhone 上 Web Speech 不可靠，iOS 仍需走 Deepgram。

2繁簡正規化

辨識引擎可能回傳簡體字。純中文（台灣）情境必須將逐字稿正規化為繁體，否則紀錄閱讀感受不佳、也不符合實務慣例。

3標點與口語贅字

中文 ASR 標點普遍不佳，加上「就是、然後、那個」等口語贅字。 這不只影響閱讀——髒輸入會直接拉低 Gemini 產出的紀錄品質。

4中英夾雜（code-switching）

台灣會議常說「這個 sprint 要先 deploy」。純 zh-TW 模型容易吃掉或音譯英文詞，多語模型反而更適合。

5專有名詞

人名、產品名、專案代號是最常錯、也最影響紀錄可信度的部分。需要術語表：可餵給辨識引擎做關鍵詞加權，也可交給 Gemini 做後修正。

＄成本現況

純中文模式 DeepL 已經歸零。若辨識改用免費 Web Speech，則連 Deepgram 也可歸零，只剩 Gemini 一次呼叫。

02 · 核心轉向

從「即時串流決定一切」到「音檔優先」

即時串流 ASR 的先天限制（片段短、標點差、無法回頭修正）在中文上被放大。 改由會後音檔產生權威版本，可一次解掉多數痛點——因為 Gemini 是「聽完整段再輸出」，不是逐字吐。

💡 這就是為什麼要「混合」而不是「取代」

上表最後三列顯示：兩條路線的強弱互補而非重疊。即時性只有串流有、文字品質只有音檔有。 因此正解不是二選一，而是兩條同時跑：現場走免費串流維持體驗與分享房間，音檔在背景累積，散會後產出權威版覆蓋。

03 · 技術可行性

Gemini 直接處理音檔：可行，且 1 小時綽綽有餘

Gemini 原生支援音訊輸入，可直接聽音檔做逐字稿與摘要，而不只是吃文字。

App 目前已有 16kHz 單聲道音訊擷取管線（原供 Deepgram 使用），加錄音不需從零開始； 但直接輸出 WAV 體積過大，應改用 MediaRecorder 壓縮編碼。

邊錄邊存與自動切割

分塊錄音

MediaRecorder 可設定 timeslice，每隔數秒吐出一塊並逐塊寫入本機—— 同時達成「邊錄邊保存」與「當機不遺失」，等同於音訊版的既有草稿救回機制。

切割的真正理由

Gemini 既然吃得下 1 小時，切割不是為了長度，而是為了上傳穩定性（手機網路斷線可重傳單塊）。 建議 10–15 分鐘一段；而紀錄生成已有分段 map-reduce 合併邏輯，可直接沿用。

⚠ 非同步處理是必要的

1 小時音檔處理需數十秒至數分鐘，不能讓單一 HTTP 請求傻等。 必須採「送出 → 建立工作狀態 → 前端輪詢結果」的非同步流程，否則會踩到連線逾時。

04 · 音檔保存策略

音檔存本機：可行，但要用對儲存層

現行逐字稿存於 localStorage，對文字沒問題，但 localStorage 僅約 5MB 且只能存字串，放音檔完全不可行。

方式適合支援度
IndexedDB直接存 Blob，容量大，最通用✓ 全平台含 iOS
OPFS邊錄邊附加寫入大檔，效能最佳✓ Chrome / Safari 15.2+
匯出下載存到「檔案」App／下載資料夾＝真正長期保存✓ 全平台
localStorage僅適合文字設定✗ 太小
Cloudflare R2（選配）跨裝置回放、可重跑△ 需先開通（通常要綁定帳單資料）

容量現實：1 小時錄音 Opus 約 15–30 MB、iOS AAC 約 30–50 MB。10 場一小時會議約 150–300 MB，一般手機可負擔。

⚠ 瀏覽器儲存 ≠ 永久保存

① 磁碟壓力下瀏覽器會清除資料，使用者清快取也會一併清掉 → 應呼叫 navigator.storage.persist() 申請常駐。
② iOS 對「未加入主畫面」的網站有閒置後清除機制 → 安裝成 PWA 後才相對安全。
③ 因此必須提供匯出音檔，那才是真備份。
④ 音訊會吃掉絕大部分空間 → 需要「錄音管理」畫面：顯示已用容量、單場刪除、N 天後自動刪除音檔（保留逐字稿）。

關鍵取捨：本機保存 ≠ 不上傳

Gemini 是雲端 API，音檔要被它聽，就一定得上傳一次。因此實際上有三種模式可選：

模式音檔去向AI 紀錄適合誰
A · 本機 + 暫時上傳建議 常駐存於裝置；產生紀錄時短暫上傳、處理完即刪，伺服器不留存 ✓ 高品質多數情況
B · 完全不外流 只存本機、永不上傳 ✗ 只能用現場即時字幕極高機密會議
C · 本機 + R2 兩邊都留，換裝置也能回放 ✓ 且可重跑需長期歸檔

✅ A 模式的隱私敘述很好講

「音檔平常只在你的手機裡，只有你按下『生成紀錄』時才走一趟，且不落地保存。」

💡 附帶好處：逐字稿點句回放

有了本機音檔，逐字稿就能點一句、跳播該段音訊。中文辨識再怎麼修，「能回去聽原音確認」 對紀錄可信度是質的提升——而每句的時間戳記系統已經存在，接起來很自然。

05 · 多人對話

Gemini 能處理多人場景，但要分清兩種能力

「分辨有幾個人在說話」和「認出誰是誰」是兩件事，Gemini 在這兩者上的表現差很多。 它的語者標記是靠提示產生的推論行為，不是專門的語者分離管線（不像 Deepgram 用聲學特徵比對）， 因此會給標籤，但不保證整場一致。

能力表現說明
依提示輸出「發言者 A / B / C」✓做得到
短音檔、音色差異大（性別／語速不同）✓通常不錯
依內容推論人名（自我介紹、互相稱呼）✓✓它的強項
長音檔標籤一致性（第 5 分鐘的 A ＝第 40 分鐘的 A？）△會漂移
音色相近（同性別、同齡）△容易混淆
搶話、重疊講話✗弱
遠場單麥克風（會議室現場）△比乾淨錄音難很多

💡 關鍵洞察：會議紀錄需要的不是完美 diarization

真正要回答的是「這個決議是誰拍板的？這個待辦是誰負責？」—— 而這件事 Gemini 反而比 Deepgram 強，因為它讀得懂內容：有人說「這部分我來處理」、 或別人喊「Mark 你負責前端」，它就能把待辦掛到正確的人身上。 Deepgram 永遠只能給匿名編號，它不知道誰是 Mark。 而 App 已有「發言者命名」編輯功能，若 Gemini 能直接填好真名，銜接格外順。

三種做法比較

做法語者一致性中文文字品質真名歸屬成本
只用 Gemini建議先做△ 會漂移✓ 最好✓只花 Gemini
只用 Deepgram✓ 穩定△ 中文較弱✗ 僅編號Deepgram
混合語者不夠穩再上✓ 穩定✓ 最好✓兩者都花

混合作法：以 Deepgram 做聲學語者切分（取得穩定的「誰在什麼時間說話」）， 再把該份帶時間戳與語者編號的稿子連同音檔交給 Gemini，請它保留既有切分、修正文字、並把編號對應到真實姓名。 切分靠聲學（穩），文字與人名靠語意（準）。

A與會者名單

會議開始前輸入「Mark（PM）、小美（工程）、John（行銷）」。 這一項對準確度的提升，比任何模型調整都大——它同時餵給辨識引擎做關鍵詞加權，並讓 Gemini 完成人名對應。

B分段時傳遞語者名單

長會議會切段處理，若各段獨立判斷，第 2 段的「發言者 A」可能不是第 1 段的 A。 必須把前段已識別的語者清單帶進下一段的提示才能維持一致—— 現有分段合併邏輯需為此補強。

06 · 建議架構

兩條並行的管線

現場管線負責「看得到」，會後管線負責「信得過」。兩者共用同一場會議的 ID 與時間軸。

現場 · 即時 維持體驗與分享，零成本

🎙 麥克風 → Web Speech免費 · zh-TW → 即時字幕 → Durable Object 房間分享連結給同事

iOS 例外：Web Speech 不可靠，改走 Deepgram。純中文若不需語者分離，可完全不開 Deepgram。

同時 · 背景 錄音與保存

🎙 同一路音訊 → MediaRecorder分塊 · 壓縮編碼 → IndexedDB本機 · 當機可救回 → 匯出檔案真備份

申請 navigator.storage.persist()；提供容量顯示、單場刪除、自動清理天數。

散會後 · 權威版 品質最高的一次產出

本機音檔 → Worker 代傳金鑰不外洩 → Gemini Files API+ 與會者名單 → 權威版逐字稿繁體 · 標點 · 去贅字 · 人名 → 會議紀錄

非同步：送出後建立工作狀態、前端輪詢。產出覆蓋即時版，並保留原始版本可比對。

07 · 實作路線圖

先確保「錄得到、存得住、清得掉」，再談送去 Gemini

每階段都可獨立交付並驗證，不必等整套完成才看得到價值。

P0

前置驗證 先做

三個「不想憑印象打包票」的項目，用小測試確認後才寫入實作假設。

  • 裝置實際可用配額：讀 navigator.storage.estimate()（iOS 實測）
  • Gemini 是否直接接受 webm/opus（文件列的是 OGG）
  • 免費層每日額度是否足以支撐 1 小時音檔的日常使用
  • Worker 大檔上傳的實際上限與逾時行為
P1

錄音與本機保存 核心

先讓音檔可靠地存在，這是後面所有功能的地基。

  • MediaRecorder 分塊錄音 → 逐塊寫入 IndexedDB（當機／關閉可救回）
  • 申請 navigator.storage.persist()
  • 錄音管理畫面：容量顯示、單場刪除、N 天後自動刪除音檔（保留逐字稿）
  • 匯出音檔到「檔案」App／下載資料夾
P2

音檔 → Gemini → 權威版紀錄

採 A 模式（本機保存 + 暫時上傳，不落地）。這是品質提升最有感的一步。

  • Worker 串流代傳至 Files API；非同步工作狀態 + 前端輪詢
  • 與會者名單輸入（人名／角色），一併餵入提示
  • 產出：繁體、補標點、去贅字、專有名詞修正、待辦歸屬到真名
  • 長音檔分段時傳遞語者名單維持一致；沿用既有 map-reduce 合併
  • 保留即時版原稿可對照，權威版可重新生成
P3

純中文模式預設 + 逐字稿點句回放

  • 首頁一鍵「純中文會議」：中文→不翻譯、自動套用分段、依平台選最佳引擎
  • 明示取捨：「開啟語者分離會改用 Deepgram，中文準度可能略降」
  • 「翻譯分段」更名為「逐字稿分段」並改寫說明
  • 點逐字稿任一句 → 跳播該段音訊（利用既有時間戳）
P4

選配強化 視實測結果

  • 術語表：人名／產品／專案代號，供關鍵詞加權與 AI 後修正
  • 混合語者模式：Deepgram 聲學切分 + Gemini 文字與人名（若實測發現標籤漂移不可接受）
  • C 模式：R2 雲端音檔保存與跨裝置回放
  • 引擎 A/B 實測工具：同一段音訊並排比較，用真實會議決定預設值

Cloudflare既有額度Worker 代傳與工作狀態；不保存音檔則不需 R2
本機儲存約 15–50 MB／小時使用者裝置空間，非金錢成本，但需管理與自動清理

相較現況（Deepgram 依分鐘計費 + Gemini），本方案在純中文情境可望把經常性費用壓到僅 Gemini 一次呼叫。

09 · 風險與待驗證

誠實的未知清單

以下項目在實測前不應寫死為設計假設。

✗ 不是即時

音檔路線是會後產出，取代不了現場字幕與分享房間——這正是要保留現場管線的原因。

⚠ 語者標記可能不夠穩

「1 小時、單麥克風、4 人中文會議」恰好是最難的組合（遠場、搶話、混語）。待驗證：是否堪用；不堪用則走混合模式。

⚠ 音檔隱私等級升級

目前只存文字，改存音訊是不同等級的資料。需更新隱私說明頁、明訂保留期限與自動刪除政策。

⚠ iOS 背景錄音中斷

切到背景或鎖屏可能中斷錄音，需靠 Wake Lock 與分塊寫入降低損失。待驗證：實機行為。

⚠ 瀏覽器儲存可能被清除

配額與清除策略因平台而異（iOS 尤其）。待驗證：以 storage.estimate() 實測；必須提供匯出作為真備份。

⚠ 格式與額度

待驗證：webm/opus 是否被直接接受、免費層每日額度是否足夠、Worker 大檔上傳上限。

10 · 需要拍板的事

四個決策點

這些選擇會改變實作方向，建議在 P1 開工前確認。

① 音檔保存模式：A / B / C？

A＝本機 + 暫時上傳（不落地）；B＝完全不外流（放棄音檔 AI 紀錄）；C＝加上 R2 雲端保存。

建議：A。隱私敘述清楚、不需開通 R2、也不必處理帳單設定。有長期歸檔需求再升級 C。

② 語者處理：先只用 Gemini，還是直接做混合？

混合品質較穩但要同時付 Deepgram，且實作較複雜。

建議：先只用 Gemini + 與會者名單，用真實會議實測後再決定是否補上 Deepgram。

③ 現場辨識引擎的預設值

純中文情境下，免費 Web Speech 的中文品質可能優於 Deepgram，但會失去語者分離。

建議：做 A/B 實測後再改預設；在此之前於 UI 明示取捨，讓使用者自行選擇。

④ 音檔保留期限

音訊佔空間且屬敏感資料，需要預設的自動清理策略。

建議：預設保留 30 天後自動刪除音檔、永久保留逐字稿與紀錄，並允許使用者調整。

✅ 建議的起手式

先做 P0 前置驗證 與 P1 錄音／本機保存，再進 P2（音檔 → Gemini）。 然後用你一場真實的中文會議實測，比較「即時版 vs 權威版」的品質差距， 再決定是否需要 Deepgram 做語者分離、以及是否要上 R2。
