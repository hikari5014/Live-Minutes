匯入錄音，
直接產出會議紀錄

不需要現場開著 App、不需要即時字幕——把任何一段錄音檔丟進來（Zoom／Teams 錄影、手機語音備忘錄、他人轉寄的檔案）， 由 AI 一次讀完、分辨講者、產出逐字稿與結構化會議紀錄。 這條路線把 Live Minutes 從「即時字幕工具」擴張成會議情報工具：現場即時只是眾多輸入之一。

是的，要獨立頁面——而且它不該只是「另一個頁面」

你的直覺對：這個流程與現場錄音心智模型完全不同（沒有會議進行中、沒有計時、沒有分享房間）， 硬塞進現有畫面只會讓兩者都難用。但我建議再往前一步—— 把它放在首頁的一級入口，與「開始錄音」並列，而不是藏在設定裡。 理由很實際：很多會議你根本不在現場開 App，錄音是事後才拿到的（Zoom 錄影、同事轉寄、手機備忘錄）。 對這些情境，「匯入」才是主要入口，不是附屬功能。

※ 本文描述的是「整段錄音一次讀取 → 分講者 → 總結」這個運作模式。 我沒有 Genspark 內部實作的資訊，因此不對其做法做任何斷言；以下所有數據皆為本專案自行實測。

01 · 現況盤點

好消息：地基已經蓋好八成

上一輪的 P2（音檔 → Gemini → 權威版逐字稿）已經把最難的後端管線做完並上線。 這次要補的主要是「檔案進得來」與「獨立的流程」，而不是重做核心。

✓已完成可直接復用

  • /api/audio：Files API 上傳 ＋ 結構化逐字稿（含講者、時間戳）
  • 講者名單跨段延續（同一人不會換編號）
  • 與會者名單 ＋ 術語表（提升人名與待辦歸屬）
  • 會議紀錄生成（長逐字稿分段 map-reduce）
  • 逐字稿編輯、講者命名、重新生成
  • 點句回放音訊（時間戳 → 音檔定位）
  • 資料夾 / 搜尋 / 封存 / 雲端備份 / 匯出

＋這次要新做

  • /import 頁面：選檔、拖放、iOS「檔案」與 iCloud
  • 檔案驗證與預檢：格式、大小、時長、額度預估
  • 單一檔案的處理管線（現有的是自家錄音的分段）
  • 處理進度與可續傳（長檔不能讓使用者盯著空白畫面）
  • 超長檔的時間視窗切分（第二階段）
  • 選配：系統分享選單接收、影片檔處理

⚠ 一個關鍵技術差異：外來檔案不能像自家錄音那樣切

我們自己的錄音是一開始就分段錄的，每段都是獨立完整的媒體檔，所以能逐段上傳、逐段辨識。 但使用者匯入的是單一容器檔（m4a/mp3/mp4），不能用位元組切割——切開就壞了。 因此匯入路線必須另設計：整檔上傳一次，再依需要用時間視窗分批辨識。

02 · 產品定位

這不只是加功能，是把入口從「當下」解放到「任何時候」

面向現在（即時優先）加入匯入後
使用時機必須會議當下就開著 App會議後任何時間，甚至幾天後
音源麥克風、分頁音訊＋ 任何錄音檔（Zoom／Teams／語音備忘錄／他人轉寄）
錯過會議沒救拿到錄音就能補做紀錄
適用內容會議＋ 演講、訪談、課程、Podcast
失敗成本現場沒開好 = 整場沒了錄音還在就能重做，且可重跑、可換語言
裝置限制iOS 抓不到其他 App 的聲音繞過了：用系統錄音錄好再匯入即可

✅ 附帶解掉一個先前無解的問題

先前結論是「iOS 無法讀取其他 App 的音訊」——這對 iPhone 上的線上會議是硬限制。 但有了匯入：使用者可以用 iOS 內建螢幕錄影／語音備忘錄先錄下來，再把檔案匯入本 App。 限制沒有消失，但被繞過了。

03 · 技術可行性

已實測的數據（非估算）

以下數字都是對本專案線上環境與 Gemini API 實際測得。

項目實測值意義
5 分鐘音檔全程往返9.2 MB · 5 秒上傳＋Files API＋辨識的基礎設施夠快，不是瓶頸
音訊 token 計費32 tokens／秒1 小時 ≈ 11.5 萬 tokens
模型輸入上限1,048,576 tokens≈ 9 小時音訊，不是限制

💡 結論：一般會議「單次呼叫」就夠了

壓縮音檔 1 小時約 15–50 MB，遠低於 100MB 上限；輸出 token 也在範圍內。 因此典型 1–2 小時會議可以整檔上傳、一次辨識完成，不需要複雜的切分機制。 切分只在超長或未壓縮檔時才需要，列為第二階段。

04 · 限制邊界

什麼可以、什麼不行

✓順暢區

≤ 100 MB 且 ≤ 2 小時的壓縮音檔（m4a / mp3 / opus）。整檔上傳、一次處理，這涵蓋絕大多數會議。

△需處理區

> 100 MB（未壓縮 WAV 約 50 分鐘就超過、或超長會議）。需時間視窗分批，或請使用者先壓縮。

△影片檔

Zoom/Teams 錄影常是 .mp4。Gemini 可讀，但影像的 token 成本遠高於音訊，會大量吃額度——需要偵測並警告，或引導只匯入音訊。

⚠ 分講者的老問題依然存在

AI 依聲音與內容推論講者，不是專門的聲學語者分離：長音檔標籤可能漂移、音色相近會混、搶話處理弱、 遠場單麥克風更難。與會者名單能大幅改善（可對到真實姓名），但無法保證逐句完美。 這點在匯入情境更明顯，因為錄音品質不由我們控制。

05 · 使用流程

六步，從檔案到會議紀錄

1

選擇音檔

點按選檔（iOS 可從「檔案」「iCloud」「語音備忘錄」匯出的檔案挑選）或桌機拖放。選配：從其他 App 的分享選單直接送進來。

2

預檢與預估

讀取格式、大小、時長，估算 token 用量與大約處理時間，超過上限時先告知並給替代做法，而不是讓它跑到一半失敗。

3

填入脈絡（選填但影響很大）

會議標題、與會者名單、術語表、輸出語言。與會者名單是分講者品質的最大槓桿。

4

上傳與辨識

整檔上傳 → Gemini 讀完 → 產出分講者、含時間戳、補標點、去贅字、繁體的逐字稿。全程顯示進度，長檔可分批並保留已完成部分。

5

生成會議紀錄

沿用既有管線：摘要、決議事項、待辦（歸屬到真實姓名）、主題重點。可換語言重新生成。

6

落地成一場「會議」

結果存成與現場錄音完全相同的資料結構——因此自動獲得：編輯、講者命名、點句回放、資料夾、搜尋、匯出、雲端備份。

07 · 路線圖

三階段，第一階段就能用

I1

可用的匯入流程 核心

目標：任何 ≤100MB 的音檔，丟進來就能得到逐字稿與會議紀錄。

  • /import 頁面：選檔／拖放、格式與大小驗證、時長偵測、token 預估
  • 脈絡欄位（標題／與會者／術語／語言），預設帶入設定值
  • 整檔上傳 → 辨識 → 生成紀錄；階段式進度
  • 結果落地成標準 session（自動獲得編輯／回放／資料夾／備份）
  • 音檔存入本機（可選不保留）
  • 首頁與錄音頁的入口
I2

長檔與韌性

  • 時間視窗分批辨識（同一份上傳檔、多次呼叫，講者名單延續）——需先驗證時間指定的可靠度
  • 可中斷續做、離開頁面不中斷
  • >100MB 的引導：建議壓縮或分割，並提供明確步驟
  • 影片檔偵測與額度警告
I3

便利性強化 選配

  • PWA 分享目標（Android）：其他 App → 分享 → Live Minutes
  • 批次匯入多個檔案
  • 從既有錄音「重跑」不同語言／不同與會者名單
  • 音檔與逐字稿的對照校閱模式
08 · 風險與待驗證

誠實的未知清單

⚠ 真實語音的處理時間未知

已測得的 5 秒是無語音音檔（輸出極短）。真實會議要生成上萬字逐字稿，時間主要花在輸出生成。待驗證：1 小時真實會議的實際耗時。

⚠ 時間視窗分批的可靠度

要求 AI「只辨識 10:00–20:00」是提示式約束，不保證精準。I2 動工前必須先實測，不可靠就改用其他切分法。

⚠ 分講者品質不可控

匯入的錄音品質（遠場、雜訊、單聲道）不由我們決定，會直接影響講者辨識。需在 UI 誠實說明，而非承諾完美。

✗ 100 MB 是硬上限

Worker 實測 120MB 即 413。超過必須在上傳前擋下並給明確替代方案，不能讓使用者等失敗。

⚠ 額度可被一次吃掉

單一長檔可能瞬間消耗大量 Gemini 額度。必須執行前顯示預估並要求確認，避免使用者無感超支。

⚠ 隱私層級再升一級

匯入的錄音可能包含使用者未參與、他人提供的會議。需在流程中提示錄音同意責任，並沿用「不落地保存」原則。

09 · 需要拍板

四個決策點

① 入口位置：首頁一級，還是收在錄音頁？

一級入口更好找，但首頁會多一顆按鈕。

建議：首頁一級（「開始錄音」下方並列），因為對事後拿到錄音的情境，它就是主要入口。

② 匯入的音檔要不要預設留在本機？

留著才能點句回放與重跑，但佔空間（1 小時約 15–50 MB）。

建議：預設保留並沿用現有保留期限設定，另提供「處理完不保留」選項。

③ 影片檔（Zoom/Teams .mp4）怎麼處理？

直接送會大量消耗額度；瀏覽器內抽取音軌很困難。

建議：先偵測並警告（標示額度較高、仍可繼續），把自動抽音軌列為之後研究。

④ 先做到哪裡？

I1 就能覆蓋絕大多數會議；I2 是長檔韌性。

建議：先做完 I1 並用你的真實錄音實測，量到真實耗時後再決定 I2 的切分策略。

✅ 建議的起手式

直接做 I1。因為後端管線已經在線上跑，這一階段主要是前端流程與輸入驗證， 工作量遠小於上一輪的 P0–P4。做完後拿一段你手上的真實會議錄音跑一次， 用實際耗時與講者辨識品質決定 I2 要不要做、怎麼做。
